JOURNEY PROPOSAL · V1

AETHERCLOUD · USER JOURNEY

用户不是来管理控制台的，而是来让每一台 AetherEdge 稳定工作的。

AetherCloud 的入口不应该是账户、API 状态或抽象总览。主入口应该回答三个问题：哪些网关需要处理、数据是否在持续到达、下一次变更是否安全。

产品入口：登录后直接进入 Fleet。第一次使用引导“添加网关”；日常使用优先显示“需要处理的网关”。审计、权限和账户退到二级管理区域。

02 · PRIMARY JOURNEY

一条主线，两个分支

主线是从“还没有网关”到“AetherEdge 持续产生可信数据”，随后才进入部署。异常不是独立产品模块，而是在每个阶段提供的处理分支。

检查心跳、时间和首批遥测

05持续观察

围绕异常和新鲜度工作

审阅、确认、等待 AetherEdge 接受

异常分支：停留在当前上下文中诊断，不把用户抛到另一个“系统状态”页面。
阶段 用户要完成的事 界面只需要回答 完成信号
进入 Fleet 判断今天是否需要行动 多少网关异常；上次数据何时到达 用户能选择一个明确对象
添加网关 创建一个可辨识的 AetherEdge 网关身份 它叫什么；部署在哪里 身份已创建，不等同于已连接
建立连接 让 AetherEdge 证明并绑定网关身份 执行哪条指令；有效期；当前进度 凭据激活并出现第一次心跳
确认数据 确认链路不是“假在线” 心跳是否新鲜；是否收到首批遥测 连接与数据都在可接受窗口内
持续观察 快速定位需要处理的网关 异常原因；影响范围；建议动作 异常被处理或明确接受
安全部署 发布一个可追踪的期望版本 变更内容；风险；AetherEdge 是否接受 Desired、Reported、Applied 可区分

03 · INFORMATION ARCHITECTURE

导航围绕对象，不围绕后台模块

一级导航保持三个工作域。进入某个 Gateway 后，遥测和部署成为这个对象的上下文，而不是新的起点。

一级工作区

  • Fleet — 默认入口，AetherEdge 网关身份、连接和健康
  • Deployments — 跨网关发布与执行结果
  • Cloud — Provider 连接、资源与放置

二级管理区

  • Members & Access — 成员、角色与权限
  • Audit — 调查时进入，不占据日常首页
  • Settings — Tenant、Project 和集成设置

05 · SUBTRACTION

明确删除什么

克制不是减少字号，而是减少用户在完成任务前必须理解的概念。

首页删除

  • API 状态大卡片
  • Tenant 与 Project UUID
  • 账户角色指标
  • 未开放模块占位卡
  • 产品权威边界宣言

接入流程删除

  • 要求用户填写 Gateway UUID
  • 常驻注册表单
  • 内部权限名称
  • Audit 与 Outbox 实现说明
  • “注册成功”等同“已上线”

视觉删除

  • 装饰性渐变和光晕
  • 每个内容都包一张卡片
  • 两套以上强调色
  • 大标题占据工作空间
  • 无含义的缩写图标

06 · DELIVERY BOUNDARY

先实现真实主线

低保真稿包含完整目标旅程，但正式界面必须继续区分已上线能力与下一阶段能力。

现在重做Fleet 空状态、列表、Gateway 详情、创建身份现有 API 可支持
下一阶段一次性 Enrollment 指令、连接等待与首批数据确认需要新 API
随后进入遥测历史、异常诊断、Desired / Reported / Applied 部署需要垂直切片
最后扩展Provider 连接、资源发现和多云放置不提前占据界面
